面向**软件宣传片**的桌面视频编辑器。Tauri v2 + React 19 + TypeScript + Vite，
一条时间线、一个所见即所得的预览、七套宣传片模板，导出为 **MP4 视频**或
**独立网页**。

品牌取自 QookiX 曲奇图标：主色 `#C97640`，深色表面 `#0b0d12 / #10131a`；
另有一套**简约米白**主题（`#FAF8F5` 底 + `#C98858` 焦糖强调 + `#3E2C20` 暖墨字），
供浅色极简风格的分镜使用。

## 快速开始

```bash
pnpm install

# 开发（纯浏览器界面，功能受限：无法读写本地文件）
pnpm dev

# 开发（完整桌面应用，可导入素材、保存工程、导出文件）
pnpm tauri dev

# 构建
pnpm build:player   # 先构建内置网页播放器 -> public/qookiv-player.js
pnpm build          # 再构建前端
pnpm build:all      # 上面两步
pnpm typecheck      # tsc --noEmit
```

> **导出网页前必须先跑 `pnpm build:player`。**
> 网页导出会把 `public/qookiv-player.js` 内联进生成的 HTML；该文件不存在时导出
> 不会失败，而是生成一个只显示工程数据的降级页面并给出中文告警。

## 架构

严格分层，依赖方向单向向下。`core` 与 `render` 不依赖 React，也不依赖任何
UI 状态——这正是"预览所见"能等于"导出所得"的原因。

```
src/
  core/          领域模型与纯函数（零依赖，可在 Node 中直接跑）
    types.ts       Project / Track / Clip / Keyframe / 主题令牌
    project.ts     工程构造、查询、normalize（关键帧裁剪也在这里）
    animation.ts   关键帧求值：路径解析 + 采样 + 颜色插值
    motion.ts      动效预设（fadeIn / riseIn / popIn / floatY…）
    easing.ts      缓动曲线（19 种）
    color.ts       颜色解析、插值、渐变
    time.ts        帧对齐、时间码、时长计算
    clips.ts       各类片段的工厂与默认值
    schema.ts      工程文件读取、容错修复、版本迁移
    theme.ts       品牌色阶与内置主题

  render/        纯 Canvas 合成器（不依赖 React）
    Renderer.ts    renderFrame(ctx, t) —— 时间点的纯函数
    layers/        每种片段一个渲染器：background / text / media / shape / device
    textLayout.ts  支持中英文混排的断行、逐字/逐词揭示
    effects.ts     转场状态机、滤镜、路径工具
    types.ts       MediaProvider 等契约

  engine/        时钟与媒体
    PlaybackEngine.ts  播放头唯一真源，rAF 驱动，不进 React state
    MediaPool.ts       解码元素池 + 逐帧精确 seek（settle）
    sharedPool.ts      预览与导出共用同一个池

  store/         editorStore.ts —— 唯一文档状态 + 撤销栈
  templates/     模板系统（types / kit / registry / apply / builtin）
  export/
    video/       WebCodecs 编码 + mp4-muxer 封装
    html/        独立网页导出（内联播放器与素材）
  player/        无框架的网页播放器，复用同一个 render/
  ui/            React 界面（App 外壳 + 预览 + 时间线 + 三个面板 + 导出弹窗）
  services/      Tauri 命令包装、素材导入、工程读写
```

### 三个关键设计决定

1. **`renderFrame(ctx, time)` 是纯函数。**
   没有内部时钟、没有累积状态。预览拖动播放头时调用它，导出器逐帧遍历时也调用
   它——同样的输入必然得到同样的像素。所有转场都写成"只作用于当前片段"的形式
   （位移、擦除、缩放、模糊），因此任何图层都能叠在任意背景上，也无需读取已合成
   的画面。

2. **播放头时间不进 React state。**
   `PlaybackEngine` 持有时间，画布、时间线游标、时间码各自订阅。60fps 播放不会
   触发编辑器的任何一次重渲染。

3. **模板是纯构建函数。**
   `build(values, ctx) => Project`。改一个参数就重建整条时间线，因此模板可以完全
   参数化；工程里只存参数值，不存模板逻辑。

## 功能

**时间线**
多轨（图层轨 + 音频轨）、拖拽移动、跨轨拖放、左右裁剪（按素材时长设限）、
在播放头分割（关键帧自动重定基准）、复制、速度调节、吸附到帧网格/播放头/相邻
片段、整段拖拽只产生一条撤销记录。轨道头可命名、隐藏、静音、锁定。

时间线上按成熟剪辑软件的习惯补齐的操作：

| 操作 | 结果 |
|---|---|
| 单击片段 | 选中（替换选择） |
| `Shift` + 单击 | 以最后单击的片段为锚点，选中同轨道上一段连续区间 |
| `Ctrl` + 单击 | 加选 / 减选单个片段 |
| 在空白处拖拽 | 橡皮筋框选，跨越所有轨道，边拖边更新选择 |
| `Ctrl` + `A` | 全选（跳过锁定与隐藏的轨道） |
| `Ctrl+X` / `Ctrl+C` / `Ctrl+V` | 剪切 / 复制 / 在播放头粘贴 |
| `Ctrl+D` | 就地复制 |
| `↑` / `↓` | 播放头跳到所选片段的**开头 / 结尾**；没有选择时跳到上/下一个剪辑点 |
| 在空白处单击 | 取消选择并把播放头移过去 |
| 拖拽媒体池中的素材 | 拖到任意轨道、任意时间点落下，落点有插入线与时长预览 |

复制粘贴会记住每个片段来自哪条轨道：粘贴时优先回到原轨道，其次落到同类可用轨道，
实在没有就自动新建一条——**粘贴永远不会静默丢片段**；并且整次粘贴只占一步撤销。

**右键菜单与结构性编辑**
在片段上右键可以得到：复制 / 剪切 / 在播放头粘贴 / 就地复制、在播放头分割、重命名、
启用停用、把播放头移到片段开头或结尾、**分离视频与音频**（仅视频片段）、**波纹删除**
（后续片段前移补位）、删除、以及**闭合该轨道的空隙**（把片段从 0 开始紧排）。
轨道名双击即可就地重命名，片段名双击也可以。

**分离视频与音频**
视频片段右键「分离视频与音频」会把内嵌音轨拆成一个独立的音频片段：

- 画面片段**就地静音**（否则会听到两遍）
- 新音频片段带着**相同的起点、时长、裁剪入点与播放速度**，因此与画面严格对齐
- **音量关键帧跟着声音走**（淡入淡出不会丢），而且是**拷贝**，之后调声音不会动到画面
- 工程里没有音频轨道时会**自动新建一条**并放在音频区
- 源文件确实没有音轨（`hasAudio === false`）时**拒绝并说明原因**，不会造出一段静音片段
- 整次操作只占**一步撤销**

> 这里有个不显眼的坑：分离出来的音频片段引用的是**视频素材**，而 `MediaPool` 原本只为
> 视频素材创建 `video` 元素、不会创建 `audio` 元素——所以分离后的声音在**预览里是无声的**
> （导出反而正常，因为导出走 `decodeAudioData` 直接解码文件）。现在按需为该素材创建一个
> 独立的音频元素：复用画面那个元素是不行的，那会把声音重新绑回画面的位置，正好抵消了
> 分离的意义。

**片段上的可视化**
- 音频片段绘制**真实波形**（对素材解码一次，按 4096 分桶取峰值并归一化后缓存，再按
  片段的裁剪起点与速度重采样到可见区间）
- 图片与视频片段绘制**胶片条**：按片段可见宽度切成若干画格（每格约 72px，最多 14 格），
  在片段的**源区间内**按下标取中心时刻采样，一格一帧；接口是按长度等比取帧，所以
  裁剪点、速度、缩放都会正确反映在画格内容上
- 关键帧在片段底部以**菱形标记**按片段内时间等比排布，**可以直接左右拖动改时间**
  （吸附到帧网格，整段拖动只占一步撤销）
- **转场标志**：`入场 / 出场` 在片段头尾各画一块半透明楔形，宽度按时长换算（最多半个
  片段）。加上 `pointer-events: none` 是必须的——那块区域有几十像素宽，吃掉指针事件就
  等于在片段中间挖出一块拖不动的死区
- 片段块的 tooltip 会列出**它到底动了什么**：`入场 模糊溶解 0.6s · 动效 宽 / 高（4 帧）`。
  菱形只说明"有动画、在哪一刻"，说不出是宽高还是模糊；路径表里没有的会**原样显示**
  （宁可露出 `props.focusX`，也不要编一个名字）。这套中文名映射在
  `src/ui/timeline/labels.ts`，是纯函数，有断言覆盖

> 视频取帧必须 `seek`，而且抽帧用的是**它自己的解码池**（`thumbnailPool`，画廊也用它），
> 不是预览那个池。这一点是硬要求：抽帧靠 seek 同一个元素实现，若和预览共用元素，**一暂停**
> 抽帧队列就会按设计结束等待、开始 seek 预览正在显示的那一帧，预览又把它拽回播放头，两边
> 打架——暂停的画面被拽去画胶片，再按播放时元素还在 seek 中途，于是"暂停/起播卡一下"。
> 抽取帧本身仍走一个单工队列：一次只处理一格，并且**播放中会暂停抽取、等暂停后再自动续上**
> （省 CPU，与正确性无关）——否则要么多个请求互相抢目标导致整条胶片都是同一帧，要么把预览
> 画面拖卡。
> 取帧时刻会**量化到网格**（每个素材约 60 个采样点），因此引用同一素材的多个片段（哪怕
> 裁剪点不同）能共用缓存，整库缓存上限 320 帧。

> 一条轨道上有时会有多个片段在时间上重叠（模板的分层就是这样），所以片段高度设为
> 32px 的泳道，既容得下缩略图与波形，也让底部的关键帧菱形有足够的抓取面积。

关键帧标记画在片段自己的那层画布上，**任何片段种类都要挂这层画布**（矩形/色块没有胶片条、
也没有波形，但它完全可能有关键帧）。这一点曾经写错过：画布只给 image/video/audio/device
挂，`shape` 被排除，于是**最常做尺寸过渡的形状上一个标记都看不到**。两个细节：

- **宽/高的关键帧画成"⇔"（浅蓝双箭头），其余关键帧仍是琥珀色菱形**——手动"尺寸过渡"和
  模板里的宽高动画都是这两个路径，所以两者都能被认出来。同一时刻既有尺寸又有别的动效时画
  菱形（信息更少、更常见）。
- **贴边的标记要夹进画布，而不是跳过**：在片段起点做过渡是最常见的用法，`x < 2` 那种写法
  会把 x≈0 的标记吃掉，于是"明明有关键帧却看不到标记"。

片段拖动的语义：一条片段只画**一行合并的菱形**，所以拖一个菱形等于"挪动这一时刻"——
该时刻上所有属性的关键帧一起移动。这样手势是可预测的，也避免了每个属性各占一行带来的
高度爆炸。抓取条上没命中菱形时会**穿透给片段本身的拖动**，不会变成一块死区。

**Alt + 拖动 = 复制一份**

在片段上按住 Alt 再拖，落点会留下副本、原件待在原处。实现是"原件跟着走、松手时在
落点补一份原件副本"，而不是"先复制再拖"——拖动途中两者观感完全一样（看不出哪份是哪份），
但拖动代码一行都不用改，**移动 + 复制一起收进同一步撤销**。

复制意图在**按下那一刻**定下来。这一点是必须的：Alt 在拖动中还兼着"临时关闭吸附"
（拖到一半按 Alt 求精确落点），如果中途按下就算复制，那个老用法会莫名其妙多出副本。
所以按住 Alt 起拖 = 复制（且本次不吸附，松手恢复），拖到一半才按 Alt = 只是不吸附。

> 复制出来的片段会**深拷贝动画曲线**：共享同一个数组的话，之后调副本的曲线会连原件
> 一起改——这类别名 bug 只在用户改副本时才暴露，所以有断言盯着。

这三样都画在片段内的单张 canvas 上，而不是 DOM 元素——一行元素的开销远大于一张
canvas；异步解码完成后通过订阅触发重绘。菱形的位置用 `(time / duration) * 片段像素宽`
计算，命中测试用同一个表达式反推，所以"画在哪"和"抓得到哪"永远一致（canvas 有分辨率
上限但会被 CSS 拉伸回片段宽度）。

**播放跟随与缩放**
播放时时间线会自动横向滚动跟随播放头。缩放（按钮或"适合"）会**锚定焦点时间**：
播放头在视野内就钉住播放头，否则钉住视口中心，避免反复缩放后视野飘走。拖动时间
尺时会在光标下方显示时间码提示。

**时间线宽度**
可滚动的网格宽度取**内容宽度与可视宽度的较大值**（内容再额外留 3 秒尾巴，方便把片段
拖到末尾之后）。缩得很小时内容会窄于面板，如果网格只到内容宽度为止，行、行分隔线和
时间尺就会**在面板中间戛然而止**，看起来像轨道被切断——剩下的部分只是空面板背景。
现在网格永远铺满面板，轨道延伸到右边缘，多出来的部分就是"没有内容的区域"。

**滚轮映射**

| 操作 | 行为 |
|---|---|
| 滚轮 | 沿时间线**左右滚动** |
| `Shift` + 滚轮 | **上下**滚动轨道 |
| `Ctrl` / `Cmd` + 滚轮 | **以指针为锚点缩放** |

触控板的横向手势（`deltaX`）同样映射到左右滚动，取两个轴里较大的那个，所以手势方向
不会拧。行模式（`deltaMode`）的滚轮事件会按行高换算，否则会被当成几个像素、手感全无。

> 滚轮监听必须用原生 `addEventListener(..., { passive: false })` 注册，不能用 React 的
> `onWheel`：React 在根节点上是以 passive 方式挂 wheel 的，`preventDefault()` 会被忽略，
> 于是 `Ctrl+滚轮` 会去缩放**整个 WebView**而不是时间线。
> 另外缩放上下限原本在视口和 store 里各写了一份（4 和 6），`clampZoom` 返回的值会被
> store 再改一次——现在统一到 `core/zoom.ts`。

**作品名称**
标题栏中间那个名字**可以直接点击修改**：回车或失焦提交，Esc 取消，空名字会被拒绝
（它会成为视频、网页和工程文件的默认文件名，空名字在磁盘上会变成 `.mp4` 和 `.`）。
悬停时右侧出现一支铅笔提示可编辑，有未保存修改时名字后面有一个橙点。
改名会同步到**系统窗口标题**（任务栏上也是这个名字），并且只占**一步撤销**。

**吸附（magnetic snapping）**拖动片段、拖动裁剪手柄、拖动播放头时都会吸附到**其它片段的头尾、播放头、0 秒**，
距离阈值是**屏幕像素**（7px）而不是秒，所以放大之后吸附自然变紧。没命中磁铁目标时
回退到**帧对齐**，所以位置永远是帧精确的。

- 拖动片段时**头尾两个边都会参与吸附**，取更近的那个——这是能把一个片段的**尾巴**正好
  顶上下一刀的关键（只吸附头的话就只能靠猜长度）
- 吸附命中时会画一条**金色引导线**，让"跳了一下"看起来是有意为之
- 按住 **Alt** 临时关闭吸附，松手恢复
- 工具栏的磁铁按钮可以整体关闭（关闭后仍然帧对齐）

**拖动时自动滚动**
把片段或裁剪手柄拖到视口左右边缘时，时间线会**持续自动滚动**（越靠边越快，最多 22px/帧），
不需要松手、滚动、再抓住手柄。关键帧拖动同样支持。

> 指针停在边缘不动时不会再触发 `pointermove`，所以自动滚动必须靠一个定时器**持续滚动**，
> 而不是"每次 move 事件滚一点"——否则恰好在你等着它继续滚的时候停下。
> 另外拖动的时间增量**必须把滚动量算进去**：视图在指针底下移动了，指针本身没动，
> 只按指针位移计算的话片段会"留在原地"、被时间线甩开。


**从素材池拖入**
图片、视频、音频都可以从左侧素材池直接拖到时间线上的具体轨道与时间点。落点会吸附到帧
网格，并有实时插入线与目标时长预览；把音频拖到图层轨（或反之）会自动改投到最近的同类
轨道，而不是拒绝。拖入的片段长度**直接跟随素材自身的时长**（探测不到时长才回退到默认值）。
实现用的是指针事件而不是 HTML5 拖放——Tauri 的原生文件拖放处理在 Windows 上会吞掉
HTML5 拖放事件。

**从系统里拖文件进来（直接落到时间线）**
把文件从资源管理器拖进窗口时：**落在时间线上就直接放上去**（和素材池拖入共用同一套落点
解析：插入线、吸附帧网格、类型不匹配改投同类轨道），落在别处则只进素材池。一次拖多个
文件会从落点开始**依次排开**，混着拖视频和音乐时各自找自己那类轨道（`sequenceDrops`）。
悬停时也有落点提示——那时还没导入文件，只按扩展名猜一个类型画提示，真正落下时再按导入
后的真实类型重算，所以猜错也不会放错轨道。

> 原生拖放给的是**物理像素**（相对 webview 左上角），而命中测试与落点换算都走 CSS 像素，
> 所以要先按 `devicePixelRatio` 折回去——不折的话，125% / 150% 缩放的机器上落点会整体偏移。
> 另外"落在时间线上"必须在**导入之前**判定：导入一个视频要探测元数据，几百毫秒后指针
> 位置早已不是落点了。

**轨道内泳道（sub-lane）**
同一条轨道上的片段**允许在时间上重叠**——合成器按数组顺序叠加绘制，模板正是靠
这一点把 Logo、标题、字幕叠在一条轨道上。但时间线一行只能画一个片段，全部画在
同一个 Y 上就会糊成一片。因此轨道内会做一次贪心区间打包（`core/lanes.ts`）：重叠
的片段被分配到纵向堆叠的泳道，同泳道内保证互不重叠。

代价是"诚实的高度"：旗舰模板 `qookix-promo` 在三张功能卡同时在场时确实有 **13 个
图层并发**，该轨道就是 13 条泳道。轨道头会显示「N 层」徽标；套用模板或打开工程
时时间线会**按内容自动调整高度**（上限为窗口高度的 62%）；预览与时间线之间的
**分隔条可以拖动**，需要更多空间直接拉。

> 若深轨道仍然显得笨重，下一步值得做的是**分组／预合成**：让一张卡片成为一个片段
> （内部含 4 个子层），而不是 4 个各自独立的片段。

**预览**
按工程原生分辨率渲染后用 CSS 缩放，与导出一致。播放/暂停、逐帧步进、跳到首尾、
循环、拖动擦洗、全屏。播放时视频元素实时播放保证流畅，暂停或擦洗时逐帧精确
seek。

**预览内的直接操作（所见即所得地摆位）**
不必回到检查器里敲数字，直接在预览画面上操作：

| 操作 | 结果 |
|---|---|
| 点击元素 | 选中（Shift / Ctrl 可加选、减选） |
| 拖动元素 | 改变 `transform.x / y` |
| 拖角点或边点手柄 | 等比缩放（绕锚点） |
| 拖顶部圆点 | 旋转，默认吸附到 15° |
| `Shift` + 拖动 | 锁定到位移更大的那个轴 |
| 拖动时靠近画面中心或其它图层中心 | 自动吸附并显示对齐参考线 |

选中框、八个缩放手柄、旋转柄、锚点十字与「名称 + 尺寸」标签都画在**同一张预览
画布**上，并且直接复用合成器这一帧实际使用的 `LayerPlacement` 几何——所以外框
不可能和像素错位。播放时这套操作层会自动隐藏，成片画面保持干净。

命中测试是逐层从上到下做的，并且会跳过接近全透明的图层，所以淡出中的元素不会
抢走点击。

**编辑位置时会带着关键帧一起走**
关键帧存的是**绝对值**，`resolveClipAt` 会用采样值覆盖基础 transform。所以在一
个「入场动画本身就驱动 `transform.y`」的片段上写 `transform.y`，画面上什么都不会
发生——这正是当初拖动只能左右、不能上下的原因（`transform.x` 通常没被动画占用）。
现在手动编辑被理解为**修改整条动效**：基础值移动，该属性上的所有关键帧同步平移
（缩放则整体等比缩放），因此曲线形状不变、元素落在你放的位置。预览拖动与检查器
输入框都走这套逻辑，输入框里显示的也是**当前时间点的实际值**。

**片段不会超出素材**
每次规范化都会检查 `源内偏移 + 时长 × 速度 ≤ 素材时长`，超出的片段会被**按可用长度缩短**
（与裁剪手柄本来就遵守的规则一致）。可达的越界途径有三条：

- 检查器里把**源内偏移**填得太大（这个输入框原本只保证 ≥ 0）
- **重新链接到一个更短的文件**（老片段仍按旧长度取源）
- 打开手工改过的工程文件

检查器的裁剪区下方会显示「素材 12.0s · 本片段使用 3.00s – 9.00s」，超界时标黄提示——
把约束**摆在用户眼前**，而不是等他发现片段悄悄变短了。

> 顺带修正一个我原本的猜测：`setClipSpeed` **保持同一段源区间**（时长按反比缩放），
> 所以改速度本身不会越界。我本来准备修这个，读了代码才发现不是它。

文字（渐变填充、描边、光晕、底板、6 种出现动画）、图片、视频、音频、形状
（矩形/椭圆/三角/星形/直线/箭头）、界面演示（浏览器/窗口/手机/平板外壳 + 截图 +

**动效与效果**
关键帧可打在任意数值或颜色属性上，19 种缓动；滤镜（模糊/亮度/对比度/饱和度/
去色/色相/投影）；11 种转场；7 种图层混合模式。

**关键帧编辑**
「动效」标签页把每个属性展开成一张可编辑表：每个关键帧都能改**时间**（拖出邻居
之后会自动重排序，否则采样会漏掉它）、改**数值**（颜色属性给取色器）、单独选**缓动**
（缓动作用在"进入该关键帧"的那一段上）、单独删除，或一键跳到该关键帧；还能在播放头
位置就地插入一个关键帧。片段上的菱形标记让这些点在做整体缩放的预览里也能看见。

**手工能做的 = 模板能做的**
模板会动画的每一个属性，属性面板里都有对应的菱形打点按钮：除了
`transform.x/y/scale/rotation`，还有 `不透明度`、`模糊`、形状与界面演示的
`宽 / 高 / 圆角 / 描边宽`、形状的 `填充色`、文字的 `颜色`、界面演示的
`取景滚动`。编辑语义按值类型分两种
（`core/propEdit.ts`）：

- **数值**：打了点之后框里显示的是**当前时间点的实际值**，输入也按"改成这个值"理解——
  整条曲线同量平移，曲线形状不变，输入的数字就是播放头下会看到的数字；
- **颜色**：颜色没法"平移"，所以改的是**播放头所在的那个关键帧**（没有就在播放头插一个）。
  "厚边收成细线"就是两个这样的点：填充从 `#241C16` 到全透明。

> 这两种语义存在的理由，是**关键帧存的是绝对值**：`resolveClipAt` 会用它覆盖基础值，
> 所以不打点的直接赋值在动画路径上等于没改。transform 的四个键早就有这层处理，
> props 之前没有——那时候「宽」打完点再改数字，画面纹丝不动。

**「界面演示」可以放图片，也可以放屏幕录像**

设备外壳里的素材不再是"只能放截图"：选一个视频素材，它就会**嵌在同一个外壳里播放**
（跟着卡片的尺寸、圆角、边框、取景滚动一起走）。这件事渲染层本来就会做——
`device.ts` 一直有 `media.getVideo()` 的回退分支——真正的拦路石在引擎里：
`MediaPool` 只用 `kind === "video"` 判断"哪个片段驱动这条视频"，于是设备片段引用的
录像**既不会被 seek 也不会被播放**，导出时 `settle()` 也等不到它，嵌在卡片里的画面
永远停在第一帧。现在两处都改成问同一个函数 `videoOwner()`（它同时认 `video` 与
`device`），并给设备外壳里的录像**强制静音**——嵌在界面卡片里的声音没有意义，
参考片的设备演示也从来没有声音。`scripts/smoke.ts` 里那条"设备片段也算视频的主人"
就是钉这件事的。

**尺寸过渡（一次点击）**
「形状」与「界面演示」的检查器里多了一块「尺寸过渡」：填**目标宽 / 目标高**与**时长**，
点一下就在播放头位置写出两个关键帧——起点是图层**此刻的可见尺寸**（带 `hold`，所以它
之前一直停住），终点是目标尺寸。多选时会带动所有选中的尺寸图层，并且共用**同一个增量**：
一叠"外框 + 截图"的边框厚度因此保持不变（`planSizeTransition`），整次操作只占一步撤销。
这就是模板里"手机卡长成桌面卡"的手工版本。

`minimal-promo` 与其它几套的气质相反：没有深色舞台、没有光斑、没有 3D 倾斜，整支

**这套模板是对照一份手写的参考实现（一个自包含的 HTML + GSAP 页面）重做的**，
所以每个时刻、每条缓动、每个像素都能追到参考片的哪一句：开场 66px 标题 +
23px/`.36em` 焦糖副标题、图标与产品名坐同一趟航班飞向左上角（名字的曲线由图标的

按 `height:0 → auto` 逐张展开）、以及 31.37s 淡入后**保持不透明**的收尾遮罩。

三处参考片能做、渲染器做不到的地方，各自的替代都写在代码里：
`clip-path` 斜向遮罩 → 英文层"宽度收到 0 + 左锚点"擦除；
CSS `skewX` → 旋转 + 加高（并解出"盖满整屏"与"只剩斜边可见"这组互相拉扯的约束）；
`overflow:hidden` 的窗口内推图 → 默认改为同长度的交叉溶解
（模板里的 `PUSH_IN_WINDOW` 可以切回推进，代价是中途会露出底下的米白）。

卡片本身只有一组参数（**含边框的尺寸 + 边框厚度**），所以换图时可以把尺寸一起动过去：
安卓段最后那张图是**原地从手机卡 1105×506 + 8px 厚边长成桌面卡 1330×866 + 1px 细边**
（宽、高、圆角、填充、描边同时插值），不是"小卡走掉、大卡进来"。

这一下**不再是写死的**：每个面板项的字段里有一个「从手机尺寸长大」开关，勾上之后
那张卡在**入场过程中**（0.45s，与推入同时开始）宽/高/圆角/边框一起插值。默认勾在
第二张卡上——它正好是第一张"桌面尺寸"的卡，也就是参考片里那次尺寸切换发生的时刻。
卡片命名也跟着面板标题走，所以改名、增删面板都不会把这套接线打断。

> 这里踩过一个自己撞上的坑：面板改成数据驱动时，`CardSpec.from` 与 `CardSpec.scroll`
> **没有任何地方再赋值**，于是 `morphOf()` / `scrollOf()` 恒返回 `{}`——两个特性一起
> 静默失效，而烟测里那条断言按**写死的片段名**（`开源项目页`）去找卡，改名后直接找不到，
> 报出来的是一句和真实原因无关的话。现在断言按"有没有在动宽/高"去找，开关是数据。

设备层为此新增了一个取景参数：**`props.scroll`（0..1 的"滚到底比例"）**，
让长截图在窗口内从顶滚到底（参考片里 GitHub 那张长图就是这么滚的）。渲染层按
"截图实高 − 取景窗高"换算成像素，所以换一张图、换一种画幅，关键帧都不用改；
它也是一个普通可打点属性，检查器里有对应的「取景滚动」滑杆。

模板里另有一个「长截图滚动」开关（面板项字段，默认关闭）：勾上后那张卡入场 0.35s
起，在 2.7s 内把 `props.scroll` 从 0 走到 1。这项**默认是关的**——普通截图被滚一遍
看起来就是画面自己在动。

**导出**
- **MP4 视频**：WebCodecs H.264 + `mp4-muxer`，可选 AAC 音轨。逐帧 `await
  media.settle()` 后才捕获画面，保证帧精确。音频链路是尽力而为的：任何环节失败
  只会产生中文告警并降级为无声 MP4，绝不会让整个导出失败。
  帧率可选 24 / 25 / 30 / 50 / 60 / **100 / 120**；H.264 级别按分辨率与帧率自动
  推导（1080p120 → Level 5.1，4K60 → 5.2），码率默认随帧率线性增长。
- **导出长度由内容决定**：时间线在哪里结束，成片就在哪里结束。
- **独立网页**：内联播放器 + 工程数据 + 素材。两种模式——"HTML + 素材文件夹"
  （大体积视频友好，磁盘上的原文件直接复制）或"单个 HTML 文件"（便于分享）。
- **单帧 PNG**：把播放头所在的一帧按工程分辨率导出（走同一个合成器，并会先
  `settle()` 等视频 seek 到位，所以存下来就是你看到的那一帧）。

> `effectiveDuration` 原本是 `max(内容时长, settings.duration)`，而
> `settings.duration` 的默认值是 **30 且从不会被更新**——于是任何短于 30 秒的剪辑
> 都会被**静默补到 30 秒**（末尾一大段黑屏）。三分钟的活干成三十秒，用户没有任何
> 线索。它本意是"作者指定的最短长度"，但一个没人维护的默认值和一个刻意的选择
> 在数据上无法区分。现在**内容说了算**，`settings.duration` 只用于**空时间线**。
> 检查器里那个可编辑的"时间线时长"也改成了只读显示，避免留一个会撒谎的控件。
> （七个内置模板的 内容 / 声明 / 设定 三者本来就完全相等，所以模板长度一分不差。）

**音频与淡入淡出**
音量是一个可打关键帧的普通属性，所以**淡入淡出就是音量关键帧**——检查器里有
「淡入 1 秒 / 淡出 1 秒」直接写入，也可以到「动效」标签页逐点微调。预览与导出走
同一条语义：预览每帧采样动画后的音量，导出则先把关键帧采样成 **10ms 步长的包络**
再驱动 `GainNode` 自动化。

> 这里有个容易漏的坑：导出原本把 `props.volume` 当常量，并且会跳过 `volume <= 0`
> 的片段。加入淡入之后，「基础音量 0、靠关键帧升起来」是完全合法的写法，却会被整段
> 丢掉——表现出来就是"预览有淡入、成片没有声音"。现在只在**没有包络且常量为 0** 时
> 才跳过，并且这条有断言覆盖。

**播放同步（媒体元素与时间线对齐）**
预览播放时，每一帧都会把「当前哪些片段应该在发声/出画」算成一个**活动集合**，
集合之外的媒体元素一律暂停——**片段结束，它的画面和声音就一起停**。

元素位置与时间线的偏差分两种情形处理：

- **暂停/拖动播放头时**：直接 seek 到精确位置（此时没有东西在播放，seek 是免费的）
- **播放中**：先容忍 0.12 秒以内的漂移，只有**连续 4 帧**都在漂移才纠正一次，
  纠正后还有 **500ms 冷却**等待解码器跟上

**最关键的一条**：合成器（`getVideo`，每帧都会被调用去画画面）**绝不允许 seek 正在播放
的元素**。播放中的元素由活动集合那套逻辑驱动，合成器只管把元素当前的画面画出来。

播放中还有两条同样关键、但症状不同的规则：

- **已经播到结尾的元素绝不再 `play()`。** 规范规定对 `ended` 的元素调用 `play()` 会把它
  **拉回开头重放**。于是"片段比素材长"（容器元数据时长比可解码流长——VFR 文件常见；或
  长度探测不到时按默认时长建的片段）会变成：元素播完 → `play()` 回到 0 → 4 帧后漂移纠正
  又把它 seek 回结尾 → 再次播完 → 再 `play()`……**画面和声音在同一段无限反复**。现在
  这类元素会被**钉在最后一帧**并保持暂停，而且 seek 目标会**夹到 `duration - 1/60`**，
  不会瞄准文件之外。
- **同一条素材在同一时刻只能有一个"主人"。** 同一个素材被多个片段引用且在时间上重叠
  （把一段复制到上层轨道就会这样）时，两个片段每帧各报一个目标位置，元素被来回拖：
  画面在两个位置之间反复跳。现在 `paintOrderTracks` 里**最后写入的（最上层）说了算**，
  它也正是画面上看得见的那一个。
- **"看着在卡"要能自己说清楚。** 至少三种成因（片段超出素材而停在最后一帧、同步在反复
  纠正、解码器跟不上），前两种 `MediaPool` 直接通过 `onSyncIssue` 报给状态栏：
  「素材只有 2.0s 而片段用到 5.0s，尾部停在最后一帧」／「播放同步每秒纠正 N 次（涉及
  「某片段」）」。健康播放**一条都不报**（有断言），否则状态栏就成了噪音。
- **暂停本身不该 seek。** 暂停的元素按**自己的帧**量化报告位置，所以"刚停下"的漂移天然是
  0~1 帧，而紧容差是 `0.6/fps`（24fps → 0.025s，而一帧是 0.042s）——于是**几乎每次暂停都会
  seek 一次**。seek 会拆掉解码器流水线，下一次播放得重新预热：用户看到的就是"暂停/继续卡
  一下，而且暂停继续次数越多越明显"。现在**刚停下的那一次取帧容忍整整一帧**（它显示的正是
  该显示的那一帧），而**擦洗与逐帧步进仍然精确**（位置真的变了，必须命中）。这跟上面那条
  是同一个教训：**容差不能小于元素的报告粒度**。另外每次暂停都会清掉该元素的同步残留
  （冷却时间、连续漂移计数、"浏览器拒绝自动播放"标记），不让状态跨暂停累计。
- **每一次 seek 都必须"记账"。** 所有赋值都走 `assignSeek`，先把目标写进 `sync.target`；
  `seeked` 处理器就是拿它判断"这次 seek 落地没有"的。曾经有几处（播放中的漂移纠正、
  暂停时的精确 seek）直接写 `el.currentTime`，于是处理器认为 seek 失败、**把元素拽回上一个
  目标**——要求它去 2s，它停在 0s。表现出来就是"每次纠正刚把画面送到新位置就被拉回去"，
  也就是**同一段一直卡**。
- **时钟是唯一权威：素材的报告值不许移动它。** 试过两次"让时钟追随素材"（想修"时钟被节流
  拖慢、漂移永远纠正不完"），两次都更糟：元素的报告值本身带量化、起播延迟和解码抖动，一旦
  让它带动时钟就会形成**跨元素负反馈**——A 的领先量把时钟往前推，B 立刻变成"落后"并被 seek，
  B 的 seek 又带来新的起播延迟，循环不止。表现是**所有视频一起卡、每秒纠正 3 次**。所以现在
  分成两件互不干扰的事：
  - **时钟自己不许丢时间**：长帧上限放到 2s（原来 0.25s，窗口在后台被 rAF 节流到 1Hz 时
    时钟只按真实时间的四分之一走——这才是"漂移永远纠正不完"的根）。有断言直接驱动引擎的帧
    回调：跳过 1.5s，时钟必须前进 1.5s。
  - **纠正必须比它修掉的问题便宜——所以播放中不用 seek 纠偏，用速度微调。** seek 会停下
    播放、丢掉解码缓冲、再花几十到一百多毫秒重新起播；拿它去修一个同样量级的滞后是净亏，
    而且会**自我维持**（seek→起播延迟→更落后→再 seek）。每次"暂停/继续"都会留下一点起播
    延迟（位置对齐了，解码器要几十毫秒才真正开始走），只"容忍"它就会**一次一次攒起来**，
    攒过阈值就进入 seek 循环——状态栏那句「每秒纠正 3 次」正是这么来的。现在播放中的纠偏是
    **改 `playbackRate`**：落后就稍微放快、领先就稍微放慢（±6% 封顶，音频 `preservesPitch`
    默认开着，听感只是极小的速度变化），回到 60ms 死区内立刻恢复片段本身的速度。只有 ≥1s 的
    **结构性**大漂移（真跳变、解码器卡死）才 seek，且连续 4 帧确认 + 500ms 冷却。

> 这里有三个真实的 bug，症状是"视频播完了里面的声音还在放""视频和音乐一起时两个都
> 断断续续"。最要命的是第三个，而且它**不在播放逻辑里，而在绘制路径里**：
>
> 1. **没有暂停已经走出片段的元素** → 元素自由跑到文件结束（"播完了还在响"）。
> 2. 播放中的对表**每帧都纠正** → 每次 `currentTime` 赋值都是一次 seek。
> 3. **合成器每帧都在 seek 正在播放的元素。** 它对表用的容差是 `0.6 / fps`，在 30fps 下
>    是 **0.02 秒**；而一个正在播放的元素报告的 `currentTime` 是**按视频帧量化**的，
>    天然就落后最多一整帧（**0.033 秒**）。**容差比元素的报告粒度还小**，所以每帧都会
>    判定"不同步"并 seek 一次——**60 帧就是 60 次 seek**，画面和元素自带的声音一起碎掉。
>    这也是为什么只修播放逻辑没有效果：真正在每帧 seek 的是画画面的那条路径。
>
> 修复的关键在于区分**谁拥有位置**：元素在播放时，位置归元素自己（由活动集合驱动、
> 宽松纠偏）；元素暂停时（拖动播放头、导出）位置归时间线，此时精确 seek 才是对的。
> 另外浏览器若拒绝自动播放，`play()` 的 promise 会 reject，这里会**报告一次**并停止对表，
> 而不是把一个原地不动的元素每帧都 seek 一遍。


**素材池**
按名称或路径搜索、按类型筛选（全部 / 视频 / 图片 / 音频）、按最近导入 / 名称 / 时长 /
大小排序，并显示「显示 N / M 个 · 已使用 K 个」。已被时间线引用的素材名称后面有一个
橙色圆点，便于判断哪些能安全删除。

> 元数据缺失（探测不到时长或体积）的素材**排在最后**，而不是当成 0——探测失败意味着
> "未知"，不是"最短的片段"。

**导出预估**
视频导出对话框在开始渲染前给出**码率与预计文件大小**（用的是导出器自己的码率推导，
不是另估一套），并在总帧数超过 4000 时提示这次渲染会比较久。网页导出会统计**被引用的
素材总量**，单文件模式下若超过 20MB 会提示 base64 内联会把体积抬高约 33%，建议改用
「HTML + 素材文件夹」。

**轨道头**
左侧轨道头是**单行**布局：类型图标、轨道名、重叠层数徽章、右侧操作按钮。头宽 208px，
按钮缩到 22px——这样「图标 + 可读的轨道名 + 徽章 + 四个按钮」才放得下。轨道名用
`min-width: 0` + `text-overflow: ellipsis` 正确省略，悬停看全名，双击改名。

> 这里踩了两个 CSS 陷阱：一是名字和按钮原本**上下堆叠**，而单层轨道行高只有 38px
> （32px 泳道 + 6px 间距），"名字 17px + 间距 3px + 一行 28px 按钮"需要约 48px，
> 于是**一直**被上下裁掉——大部分轨道都是单层，所以看起来永远在溢出；
> 二是 `text-overflow: ellipsis` 写在了 flex 父容器而不是真正持有文本的 span 上，
> 完全不起作用，名字被从中间硬切。另外 flex 子项默认 `min-width: auto`，nowrap 文本
> **不会收缩**，会把徽章顶出容器。

**自动保存与崩溃恢复**
只要工程处于「有未保存修改」状态，就会被节流镜像进 `localStorage`（编辑停止约 1.2 秒后
写入），**保存成功后立即清除**。因此"存在自动保存"本身就是"上次退出时确实丢了东西"的
信号——不需要时间戳比较，也不需要判断上次是否干净退出。

下次启动会弹出恢复对话框，列出工程名、最后自动保存时间、片段/素材数量与原保存位置，
可以恢复（恢复后仍标记为未保存，万一再崩一次网还在）或丢弃。关闭窗口时若仍有未保存修改
也会补写一次。记录读取时同样过一遍 `parseProject`，所以写了一半或手改过的记录会被修复
而不是抛异常；本地存储不可用或已满时只提示一次，绝不打断编辑。

**轨道管理（右键轨道头）**
上移一层 / 下移一层、复制轨道（含全部片段）、闭合该轨道的空隙、清空轨道上的片段、
删除轨道。重排只在**同类型轨道之间**交换，音频与图层两个区段不会互相穿插。

**素材重链接（离线媒体）**
文件被移动或删除后，媒体元素会触发 `error`，`MediaPool` 把它标记为**离线**并广播；
素材库里该条目变黄并给出提示，点「重新链接」指回文件即可。**重链接保留素材 id**，
因此时间线上的片段、裁剪点与关键帧全部原样保留，工程是就地修好的。导出对话框会在
开始渲染前先警告"有 N 个在用素材已离线"，避免等半天导出一堆占位图。

## 验证状态

诚实说明，避免高估完成度。

已实际验证：
- `pnpm typecheck` 零错误（strict + `noUnusedLocals`）。
- 前端生产构建通过（1962 个模块）。
- 播放器 IIFE 构建通过（`public/qookiv-player.js`，约 46 KB）。
- `cargo check --offline` 通过，含新增的 `write_base64_file` 命令。
- **无头引擎冒烟测试**（`scripts/smoke.ts`，通过 `vite.smoke.config.ts` 打包后用
  Node 运行）：装入一套假 canvas，对全部 7 套模板各渲染 91 帧——无异常抛出、无
  NaN/Infinity 进入任何 canvas 调用、无关键帧越界；逐轨道断言**同泳道内不存在时间
  重叠的片段**；并用服务端渲染跑通整棵 React 界面树（约 39k 字符标记）与两条导出
  流水线的模块加载。

这个测试抓到过四个真 bug：

1. 三套模板的关键帧越过片段结尾（出场淡出只走到 92% 就硬切）——现已在
   `normalizeProject` 里统一裁剪。
2. 时间线泳道打包的回归保护（同泳道内不得有时间重叠的片段）。
3. **带入场动画的片段无法被拖动**——旗舰模板 27 个片段里有 12 个动画了
   `transform.y`，写基础值会被动画覆盖，表现为「只能左右拖」。
4. **拖一下就飞出去**——`applyTransform` 从当前片段而不是快照读取动画曲线，于是
   每次 pointermove 都在已偏移的曲线上再偏移一次总位移，位移按平方增长。现在断言
   「15 次移动事件后总位移必须正好等于目标位移，且重复应用同一目标不得再次移动」。

预览几何也在其中被断言：`localToProject` 与 `projectToLocal` 必须互为精确逆变换
（否则选中框会从元素上滑走），且最上层元素中心点的命中测试必须命中它自己。

属性关键帧的手工编辑同样被断言（`core/propEdit.ts`）：没打点时改数值**不得凭空生成
关键帧**；打了点之后改数值必须**让整条曲线同量平移**——播放头下的可见值等于输入值、
关键帧数量不变、曲线跨度不变、顺序不破，而且**连续 5 次改成新目标后必须正好停在第 5 个
目标上**（累积式实现会飘出去）；颜色改动必须**写进播放头那一帧**（同一时刻重复写只是
替换，不产生重复关键帧），未打点的颜色路径则只改基础值；尺寸过渡写出的两个关键帧必须
落在片段内、起点带 `hold`（否则整段都在慢慢长大）；「外框 + 截图」共用一个增量时
**边框厚度必须保持 16px 不变**，且整次操作**只占一步撤销**（这条直接驱动 store 走
工具的完整路径）。JSX 那一层只过了类型检查：SSR 下 zustand 读的是 `getInitialState()`
快照，渲染不到"选中了片段"的分支。

时间线上的动效标签同样是纯函数、同样被断言：已知路径必须映射成中文（`props.width` → 宽）、
**路径表里没有的必须原样露出**（不许编名字）、空的关键帧数组不算"有动画"、关键帧总数正确、
转场摘要格式正确，并且**模板里那张做尺寸过渡的卡，摘要里必须看得出"宽 / 高"**——否则
时间线上就只剩下两枚说不清含义的菱形。

Alt + 拖动与多文件拖入也直接驱动 store 断言：移动 + 复制**必须只留一步撤销**，而这一
步撤销要**同时**把移动和复制都收回去；副本的动画必须是**深拷贝**（改副本的曲线不得动到
原件）；一次拖入 3 个文件时第一个落在指针处、其余**按各自时长依次排开**，混着拖音频时
**必须归到音频轨**；落在锁定轨道上要**改投同类可用轨道**而不是拒绝；`addClips` 插入
一批片段并登记新素材时**只占一步撤销**、并选中整批。

`minimal-promo` 另有一份**版式几何审计**（`.scratch/layout-check.ts`，跑的是真实
合成器，只是用假 canvas 估算文字宽度）：逐帧断言「左侧文案栏不被任何不透明卡片压住」
「注释气泡可见时必须 95% 以上贴在卡片上」「四条扫场都真的盖满整屏、且每条切片的
**横边**始终留在画面之外」「手机卡到桌面卡的尺寸过渡真的在动宽高与边框」「同一时刻不得
有两条清单同时亮着」。它抓到过六个只看代码看不出来的问题：

1. **开场 Logo 从第 0 帧就往左飘**——关键帧是绝对值，`hold` 帧必须落在"开始移动"的
   那一刻，而不是第 0 秒；
2. **注释气泡按左边缘给坐标却按中心摆放**，整块偏了半个宽度，有一半飘在卡片外；
3. **飞出去的旧卡横穿文案栏**，深色字压在深色卡上糊掉约半秒（改成离场头 0.26 秒淡干净）；
4. **换语言的焦糖切片扫过整屏时同样压住了文案栏**（改成只在卡片范围内扫过）；
5. **斜切转场能看出"三个歪掉的正方形"、四角还会漏出米白底色**——参考片用 CSS
   `skewX`，上下两条边本来就在画面外；形状层没有 skew，只能用旋转逼近，而旋转 20° 的
   矩形要沿自己的短轴覆盖 `1920·sin20 + 1080·cos20 ≈ 1672px` 才盖得住，原来只给了
   1382px，于是横边扫进了画面、四角也露底。改成 2200px 后只剩两条斜边可见；
6. **注释气泡比卡片先出现**（7.45s 淡入，而卡片 7.59s 才开始进画面），浮在一片空白上；
   现在等卡片推进到位再出现。

另外修了一个渲染器里的字距问题：`layoutText` 把 letter-spacing 摊进每个字的步进来算
宽度，但**绘制路径从没设置 `ctx.letterSpacing`**，于是画出来的墨迹比它自己的文本框窄，
居中/右对齐的文字整体偏移约半个字距——参考片那种 `.36em` 的副标题会偏左 33px，落版
右对齐标题偏左 18px。左对齐看不出问题（行内偏移本来就是 0），所以一直没被发现。现在
整段绘制时把字距交给画布（逐字揭示路径仍用自己算好的步进，否则会重复计一次）。

> 这个环境没有浏览器，所以**画面好不好看仍然没有被验证过**：几何是对的，节奏是按参考
> 片排的，但配色、字重、留白这些只能靠眼睛判断的东西，需要在编辑器里套用一次再看。

时间线几何与剪贴板同样被直接断言（store 是纯 zustand，无需浏览器即可驱动）：
行布局必须首尾相接且总高等于各行之和；整屏框选要多于少都不行、空框选不得命中；
剪辑点必须严格递增且覆盖每个片段的头尾；复制两段带间隔的片段后在 40s 粘贴，
**相对间隔必须保持、不得复用 id、且整次粘贴只消耗一步撤销**。

波形峰值与结构性编辑也在断言范围内：静音输入不得产生 NaN 或除以零、峰值必须归一化
到 1；波纹删除必须**把后移的片段正好左移被删除的时长、且不得移动在它之前就结束的
片段**；闭合空隙之后各片段的起点必须严格首尾相接。

音频包络与重链接同样被断言：包络必须从静音开始、以静音结束、中点接近满幅、全程落在
0..1；**基础音量为 0 但带淡入的片段必须仍然被收集进混音**（这正是"预览有淡入、成片
没声音"那个坑）；重链接之后素材 id 必须保持不变、元数据必须刷新、且片段仍指向同一个
素材（不得被孤立）。

关键帧拖动也有一组断言：一次移动必须**同时作用于该时刻的所有属性**、不得扰动其它关键帧、
移动后列表仍须保持按时间升序（采样依赖这个前提）；**10 次连续移动事件之后关键帧必须
正好停在目标位置**（累积式的实现会把它推出去很远）；并且拖动过程使用 `history: false`，
**不得塞进多余的撤销记录**。

自动保存与轨道管理同样被断言（`localStorage` 在测试里被打桩）：自动保存必须能完整往返、
保留文件路径与片段数、**损坏或截断的记录必须被修复而不是抛异常**、**存储写入抛错时必须
返回失败而不是崩**；新增图层轨道**不得插到音频轨道后面**（否则区段会交错，界面顺序也不对）；
重排只在同类型之间交换、到顶时为空操作；复制轨道**不得复用原片段 id**。

素材池排序与导出估算也被断言：排序**不得修改调用方的数组**、四种排序顺序正确、
**元数据缺失的素材必须排最后**、搜索大小写不敏感且空查询匹配全部；导出估算必须随帧率
增长，且 32 秒 1080p30 的估算落在合理区间（不是几十 MB 也不是几 GB）。

胶片条采样同样被断言：量化必须**幂等**、同一格内的两个时刻必须**共用缓存键**、相隔一格的
必须区分；画格数**永不为 0 也不超过上限**、随宽度增长；画格时刻必须**严格递增且不越出片段
的源区间**、从画格中心而不是入点开始采样、并且**跟随播放速度**拉伸。**关键帧标记**另有断言：
带关键帧的**形状必须也挂上标记画布**（这条抓的正是"尺寸过渡没有标记"）、宽高关键帧必须是
**尺寸类标记**且落在关键帧时刻上、同一时刻的普通关键帧**优先画菱形**、空形状**不多挂**一层
画布、媒体片段照旧有画布。另外还盯着接线——**请求一个胶片帧只许动胶片池的元素，预览的元素
一次都不许碰**（这条抓的正是"暂停/起播卡一下"）。

播放同步用**打桩的媒体元素**直接断言（记录 `play`/`pause` 调用次数与 `currentTime` 赋值
次数，后者即 seek 次数）：片段结束或还没开始时元素**必须被暂停**；元素与时钟同步推进时
**一次 seek 都不允许有**；而一个"seek 还没落地"的持续偏差在 60 帧里**最多只允许纠正 2 次**。
测试替身还会**按规范把 `ended` 元素上的 `play()` 拉回开头**——没有这一条，"播完被同步
循环重新播放"这个 bug 在测试里根本不会现形。

配套的几条：**片段比素材长**时元素必须停在最后一帧（`playCalls` 必须为 0、位置不许再动、
钉住只允许一次 seek，并且**只报一次**"素材比片段短"、要带上素材真实长度）；**暂停不该
seek**（0.72 帧的漂移不许 seek，否则每次继续都要重建解码器），但**暂停后擦洗与逐帧步进
必须仍然精确**——而且**4 秒的漂移当然必须 seek**（这条是旧断言替我抓住的：我第一版把
"刚停下"写成了"这次一定不 seek"）；**健康播放一条同步问题都不许报**、**只纠正一次也不算卡**；**两个重叠片段共享同一素材**时 60 帧内**一次 seek 都不允许有**，
且元素必须跟着**最上层**那个片段走（这正是"画面在两个位置之间反复跳"的成因）；
**要求它去 2s 就必须停在 2s**（这条抓的正是"seek 没记账 → 被 `seeked` 处理器拽回旧目标"
那个 bug），而**真跳变（`exact`）反过来必须回拽**；**两个视频一起播**时，其中一个领先
0.3s（解码缓冲的正常余量）必须是**放慢一点去等时钟**（`playbackRate < 1`）而不是 seek，
与时钟同步的那一个必须**保持片段本身的速度**、**60 帧内零 seek**；**反复暂停/继续 6 次**、
每次注入 0.08s 起播延迟之后，偏移必须仍 **≤60ms**（不许攒起来）、**一次 seek 都没有**、
而且**确实用了速度微调**、追平后**速度精确回到 1**；**真正的 2s 漂移**仍然必须 seek，
并且**seek 之后必须停下来**；**引擎的时钟在 1.5s 的长帧里必须前进 1.5s**。

最关键的一条：让元素**以视频帧的粒度**报告位置（播放中真实元素就是这样，天然落后不到
一帧），然后跑 60 帧合成 —— **seek 次数必须是 0**。修复前这里是 **60 次**。
这组断言在把修复注释掉之后确实会失败，不是摆设。

素材到片段的默认值也被断言：60 秒的视频**必须得到 60 秒的片段**（这里曾经被硬性截断到
20 秒，是"拖进来时长不跟视频长度"的真正原因——时长探测本来就是好的，是上限把它丢掉了）、
音频同理；只有**探测不到时长**时才回退，且回退值合理。

分离视频与音频同样被断言：画面片段**必须被静音**、新音频片段必须带上**相同的起点/时长/
裁剪入点/速度**、音量关键帧必须**迁移且是拷贝**（不得与原片段共享数组）、没有音频轨道时
必须**新建一条并落在音频区**、源文件没有音轨时必须**拒绝而不是造出静音片段**、
整次操作**一步撤销**；以及最关键的——分离出的声音在预览里**必须能解析到音频元素并真的
开始播放**（这一条在去掉按需元素后确实会失败）。

滚轮映射用一个假滚动容器断言（记录 `scrollLeft`/`scrollTop` 并按真实行为钳制）：
滚轮必须**只**横向滚动、`Shift` 必须**只**纵向滚动、`Ctrl` 必须**只**缩放且
**必须调用 `preventDefault()`**（否则缩放的是整个 WebView）、`Ctrl` 缩放**不得同时滚动**、
行模式增量必须被换算、指针锚点缩放的方向必须正确、上下限必须钳制、卸载后监听必须真的移除。

吸附规则直接断言（纯函数）：目标集合必须包含每个片段的**头尾**、0 与播放头，且**不得包含
正在拖动的片段自身**；拖动时**头或尾任一命中都必须吸附，取更近的那个**（尾吸附正是旧实现
做不到的情形）；超出容差时必须**回退到帧对齐**且不报命中；容差必须是**像素**——同一个
5px 距离在 100px/s 下吸附、在 400px/s 下不吸附；空目标列表与 0 缩放下**不得产生 NaN**。

自动滚动与拖动增量也被断言：视口中部**不得**触发滚动、左右边缘必须分别给出反向/正向滚动、
速度必须有上限、贴边时 `tickAutoscroll` 必须真的推进 `scrollLeft` 且**回到 0 处不得越界**；
拖动增量必须把**视图滚动量**计入——指针完全不动而视图右移 200px 时必须得到 2 秒而不是 0，
视图左移 100px 时必须**正好抵消** 100px 的指针位移。

导出长度同样被断言：**3+3 秒的剪辑必须报 8 秒而不是默认的 30 秒**，并且**导出计划**本身
（真正会被渲染的帧数）也必须是 240 帧而不是 900 帧；空时间线仍要回退到设定值；
尾部超出设定值的片段**不得被截断**；被停用的片段**仍然占据时间**；七个模板的长度
**一个都不能变**。（这条断言在恢复旧规则后确实报出 "the export plan renders 30.00s for
8s of content"，不是摆设。）

作品名称同样被断言：改名必须**写进工程名、标记为未保存、且只占一步撤销**；
新名字必须出现在**导出的网页标题**里；空名字导出时必须有可用的回退名。

时间线网格宽度同样被断言：短工程缩到最小时网格**必须仍有整个面板那么宽**
（这正是"轨道断一半"的成因）、长工程在高缩放下**仍由内容决定**、任何时长与缩放下都
**不得窄于面板**、未测量到视口时回退到内容宽度、末尾**必须留出拖放余量**、
以及 NaN 时长 / 0 缩放 / NaN 视口宽度**都不得产生非有限值**。

素材边界同样被断言：任何片段的 `源内偏移 + 时长 × 速度` **不得超过素材时长**（只允许
一帧的余量，因为片段本身不允许短于一帧）；源内偏移超过素材末尾时必须被拉回；
**重新链接到更短的文件后使用它的片段必须一起变短**；**七个模板的每一个片段都不得越界**
（这条直接在真实数据上验证不变量）；**素材长度未知或素材缺失时不得擅自截断**；
图片与纯形状不参与该检查。（去掉约束后这组断言会报出 4 条越界，包括"重链接到 3 秒文件后
仍需要 9 秒"这条。）

尚未验证（本环境没有浏览器/WebView）：
- 真实播放、擦洗、拖拽的交互手感。
- 真实的 WebCodecs 编码：`avcC` 元数据是否被 `mp4-muxer` 正确接收、AAC 编码是否
  可用（不可用时按设计降级为无声并告警）、硬件编码器对 codec 字符串的接受度。
- 网页导出的实际内联结果与播放器在浏览器中的表现。
- `asset:` 协议下 `fetch()` 取素材是否被拦截（若被拦截，音频会降级）。

首次运行 `pnpm tauri dev` 会编译 Rust 后端，需要几分钟。

## 已知约束

- **构建需要写工作区之外**：本机的 pnpm 全局存储锁与 cargo 缓存位于用户目录下，
  受限沙箱内 `pnpm add` / `cargo build` 会被拒绝，需要放宽权限执行一次。
- **`pwsh` 无法在此工作区创建文件**（只能建目录），因此本仓库的文件均由编辑器
  工具写入；手工用 `Set-Content` 之类命令写文件会失败。
- `mp4-muxer@5.2.2` 已被作者标记为 deprecated（后继为 `mediabunny`），当前功能
  正常；未来升级只需替换 `src/export/video` 里的封装层。
- `public/qookiv-player.js` 是构建产物，已加入 `.gitignore`：新克隆的仓库在导出
  网页前需要先跑一次 `pnpm build:player`。

## 贡献

欢迎提 issue 和 pull request。动手之前跑一遍：

```bash
pnpm install
pnpm typecheck   # 必须零错误（strict + noUnusedLocals）
pnpm smoke       # 无头冒烟测试：七套模板、泳道打包、播放同步、导出流水线
```

`pnpm smoke` 会先把 `scripts/smoke.ts` 连同真实引擎打包成 `.scratch/smoke.js`，
再用 Node 跑一遍（这个环境没有浏览器，所以用假 canvas 顶替）。

改动如果碰到「看起来早就修好、其实是踩过坑」的行为（上面那些引用块里记的每一条），
请顺手在 `scripts/smoke.ts` 里补一条断言——**把修复注释掉之后它必须会失败**，
否则它只是在描述现状，不是在防回归。

提交粒度上，一个提交只做一件事。
